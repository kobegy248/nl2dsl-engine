# NL2DSL 下一阶段：企业受控试点路线

> 日期：2026-09-27。基于项目提交 `503204c` 的静态核对。
> 背景与证据：[企业级能力调研与项目对标](../reports/2026-09-27-enterprise-nl2dsl-landscape.md)。
> 本文是规划，不代表功能已经实现、测试已经通过或已经具备生产认证。

## 1. 阶段目标

把项目从“完整查询链路的工程原型”推进到“可在明确边界内交付的企业语义查询服务”。核心验收对象不是演示问题数量，而是：

1. 只能由可信身份访问被授权的业务数据和元数据。
2. 支持范围内的业务问题，返回可独立验证的正确答案。
3. 配置发布、模型变化和物理优化不会悄悄改变业务口径。
4. 用户可以完成澄清、追问、解释和反馈，运营人员可以追溯失败原因。
5. 在约定负载下，有执行时限、资源上限、故障恢复和可复现交付方案。

产品定位建议：**面向企业内部应用和 AI Agent 的可治理语义查询服务**。Web 是试点用户入口，REST 是主集成接口，MCP 是后续薄适配层；三者必须使用相同的授权、DSL 校验、编译、执行和审计能力。

## 2. 试点边界

| 项目 | 建议范围 |
|---|---|
| 业务域 | 一个有业务专家负责的领域；没有外部资源时先用 ecommerce 验证工程闭环 |
| 租户 | 至少两个租户，包含相同业务 ID、相同问题及不同授权范围的隔离用例 |
| 数据库 | 一种真实生产候选数据库；无既定约束时优先评估 PostgreSQL，最终以试点环境为准 |
| 语义资产 | 首批 20–30 个经过业务确认的指标及其必要维度，不为凑数量虚构定义 |
| 问题范围 | 明确支持的聚合、过滤、时间、分组 TopN、占比；越界问题应澄清或拒绝 |
| 会话 | 3–5 轮的短分析任务；暂不做跨领域自主长任务 |
| 用户 | 首轮约 5–10 位业务用户，不直接面向全公司开放 |
| 数据安全 | 只读业务库凭据、脱敏结果、最小化日志；禁止用真实密钥或未脱敏业务数据制作评测提交 |

六周是依赖顺序和里程碑建议，不是交付保证。建议有一名持续开发人员、固定参与验收的业务负责人，以及可用的测试和部署环境。若同一人兼顾开发、业务定义与运维，宜按 8–10 周安排；AI 辅助开发不能替代业务口径和权限验收。任何安全门槛未通过，均不得为了周数继续扩大接入范围。

## 3. 优先级与设计约束

### P0：先封闭可信执行边界

**可信身份**

- 接入现有 OIDC/JWT 身份提供方或经过验证的企业网关身份，不自行建设完整账号系统。
- 校验签名、签发者、受众、过期时间；由服务端生成统一主体上下文，包含用户、租户、角色、允许访问的业务域和数据源。
- 请求中的 `user_id`、`tenant_id` 不能覆盖认证主体。租户切换如有业务需要，必须显式验证成员关系，不能仅相信请求参数。
- 未知用户、缺失策略、未知领域和未授权数据源默认拒绝。开发 Mock 身份必须显式开启，生产配置禁止开启。
- 查询、流式查询、直接 DSL/执行接口、元数据、审计、反馈和 `/query/resume` 都纳入同一策略；RAG 检索范围也必须受授权约束。
- 可信身份接入后，重新检查行级、列级、敏感字段脱敏在所有执行路径中的一致性。管理员与普通用户的操作边界必须有独立测试。

**语义正确性**

- 先为 `like` 在不同索引统计配置下改变结果的行为建立反例，再修复编译逻辑。
- 明确定义包含、前缀、后缀和模式匹配的 DSL 语义，兼容既有 `like` 契约；不能只改名字而使旧请求静默变义。
- F006 的模糊匹配转精确枚举，必须有受控值解析的等价证据。没有充分证据时保留原语义或澄清。
- 同一授权上下文、同一数据快照和同一语义版本，修改索引、行数、选择性或启停优化器，不应改变业务结果。
- 不以禁用治理或吞掉错误来提高通过率；warning 携带真实结果的既有契约需要保留回归测试。

### P1：把语义配置变成可发布的契约

先沿用 Git/YAML，不建设完整建模平台：

- 为资产增加 schema 版本、负责人、业务定义、单位、时间粒度以及必要的关系基数约束。
- 区分业务语义版本、权限版本与物理统计版本；物理统计更新不得引起业务语义变化。
- 校验指标引用、表达式、维度、value_map、连接键和可达性。对可能重复计数的多对多或不明确粒度连接，先明确拒绝，不承诺自动修正所有复杂 Join。
- 发布产物使用不可变快照和内容 hash。每个请求固定使用一份快照，审计记录对应语义版本、权限版本和物理配置版本。
- 发布前跑测试和回归集；保留上一版，验证回退流程。权限撤销应在下一次执行前重新校验，不能让旧会话沿用过期授权。
- 反馈进入候选资产后，需要人工审核、独立回归和显式发布，不直接在线自动改写受信指标或提示词。

### P1：结果级质量门槛

复用现有 V2 runner、Observation、基线 hash 和矩阵，增补缺口，不重写评测框架：

- 保留 DSL 语义维度分数作为诊断指标，另设独立的结果正确性、安全性与任务完成断言。
- 标准答案来自业务人员确认的结果或人工审阅的基准 SQL，不能由被测 DSL 编译器同时生成实际与期望结果。
- 固定数据快照、参考日期、时区、权限主体、模型/提示词/语义版本及参数。对数值容差、空值、重复行、排序和空结果分别定义比较方式。
- 区分“应回答”“应澄清”“应拒绝”“基础设施失败”；非成功响应不一律视为零分，执行成功也不自动等于回答正确。
- 开发示例、调优集和保留集按业务意图/模板分组隔离；同一问题的改写不跨组泄漏。保留集答案不进入 RAG 或生成提示。
- 加入变形测试：不同物理统计下结果一致；优化器 on/off 结果一致；缩小权限不会扩大可见结果；跨租户无法复用他人的会话、缓存或反馈。
- 确定性测试进入每次变更门槛，真实 LLM 测试显式启用并设置预算。报告缺少数据或外部依赖失败时标注未验证，不伪装通过。

### P1：多轮使用和生产执行

- 会话保存明确的 DSL 语义状态、澄清项和版本关联，而不是无限拼接聊天原文。每轮重新授权、校验、扫描和执行。
- 会话与租户、用户、领域绑定；审批恢复还要校验审批角色、过期时间、操作幂等性和目标查询归属。
- 持久化会话检查点，验证重启后恢复。不默认长期保存完整查询结果，定义留存和脱敏策略。
- 前端接真实流式事件，展示可操作的澄清、业务口径、真实 Trace 与反馈入口；不把澄清显示成系统错误。
- 先为一种数据库实现只读连接、数据库级语句超时、取消和结果上限。HTTP 超时或事后计时不等于数据库查询已停止。
- 业务只读凭据与需要写入审计/反馈的存储职责分离。增加有界并发、队列和模型调用预算；同步数据库调用不得长期阻塞 API 事件循环。
- EXPLAIN 仅作为方言相关的风险预估；失败时明确采取保守策略，不将未知成本当作低成本。不要把 SQLite 的 SCAN 启发式称为通用生产成本估计。

### P2：受控的 Agent 接口

通过前述门槛后再增加只读 MCP：指标发现、受权语义查询、DSL 校验和口径解释。MCP 调用方身份映射到统一主体上下文，租户由可信身份确定。

不要提供任意 SQL 执行、任意文件读取、权限配置修改或无范围的数据源枚举工具。MCP 只适配现有应用服务；必要时从路由抽取最小共享调用层，不复制一套查询引擎。

## 4. 六周建议路线

| 周次 | 主题 | 主要工作 | 当周退出条件 |
|---|---|---|---|
| 第 1 周 | 身份与语义底线 | 完成入口清点、可信主体接入、未知身份默认拒绝；修复 `like`/F006 语义风险；收集首批 20–30 个业务标准问题 | 请求无法伪造其他租户；未知用户不能无策略查询；匹配语义反例及 warning 保留数据测试通过 |
| 第 2 周 | 语义资产发布 | YAML 校验、负责人和必要粒度/基数定义、不可变版本快照、发布与回滚；给元数据和 RAG 加授权范围 | 非法资产不能发布；风险 Join 被拒绝或有已验证方案；请求可定位语义/权限版本；回滚演练成功 |
| 第 3 周 | 答案与安全评测 | 扩展 V2 结果比较器、分类期望、保留集隔离、当前版本基线、CI 门槛和真实 LLM 受控矩阵 | 生成可复现报告；分别给出结果正确率、澄清/拒绝表现、安全断言和执行失败率；不再引用六月报告代表当前版本 |
| 第 4 周 | 会话与反馈闭环 | 持久会话、DSL 状态增量、澄清继续、审批恢复身份校验；前端流式事件、Trace、口径和反馈连通 | 3–5 轮业务任务可完成；跨租户/跨用户会话访问被拒绝；重启可恢复；用户反馈能进入审核候选 |
| 第 5 周 | 单数据库生产保障 | 一种真实数据库的超时、取消、只读、行数限制、并发限制；结构化延迟/成本观测；去除本机路径依赖 | 干净环境可启动；压测报告标注数据量和并发；超时后数据库确实停止执行；审计/反馈备份恢复演练通过 |
| 第 6 周 | 受控试点与接入 | 5–10 名用户完成限定任务；复盘错误、成本和接入时间；有余量时做只读 MCP 验证 | 达到试点门槛且业务负责人认可后扩大范围；MCP 未完成不阻塞试点，安全或正确性未通过则不扩围 |

测试不是集中在第三周才开始：每周变更都要有对应单元、集成和安全回归。第三周负责把这些测试组织成独立、可比较的发布评价体系。

## 5. 建议验收门槛

以下是项目建议目标，**不是行业统一数据，也不是当前已达到的指标**。第 1 周与业务负责人确认范围后冻结；不得通过删除失败用例或事后缩小分母达标。

| 维度 | 建议指标 | 计分与约束 |
|---|---|---|
| 身份与隔离 | 已定义安全回归集 100% 通过 | 覆盖缺失/伪造/过期身份、未知策略、跨租户、敏感字段、元数据、审计、反馈、恢复和各查询入口；只说明测试范围内通过，不代表绝对安全证明 |
| 答案正确性 | 支持范围内保留集结果正确率至少 90%；已认证核心高频场景至少 95% | 最终验收建议至少 100 个独立可回答场景；用例与答案由业务方确认。失败、超时、错误澄清计入可回答场景分母 |
| 语义优化 | 固定样本下优化器 on/off 与物理统计变化的结果等价断言全部通过 | 不保证输出 SQL 一致；比较的是相同数据及权限下的业务答案。治理拒绝与明确不支持另行分类 |
| 澄清与拒绝 | 关键歧义和越权场景全部符合预期；普通歧义单独报告 precision/recall | 不将全部问题拒绝当作安全且高质量的问数能力；可回答问题的错误拒绝必须计错 |
| 多轮任务 | 至少 30 个独立任务，3–5 轮完整完成率建议不低于 85% | 包含时间修改、增加过滤、换维度、澄清、重启恢复及跨用户隔离；不能只测每轮接口返回 200 |
| 延迟 | 初始参考：简单查询端到端 P95 不高于 10 秒，受控复杂查询不高于 30 秒 | 第 1 周根据模型和数据库确定最终 SLO；报告样本量、冷/热状态、并发 5/10、数据量和排队时间，不能拿 Mock 耗时承诺真实体验 |
| 成本与资源 | 每租户有明确调用预算、并发和结果上限；记录单次成功任务成本 | 预算金额由试点确定；达到上限后明确拒绝或排队，不静默降低权限或语义准确性 |
| 可追溯性 | 验收样本均能关联身份、领域、语义/权限版本、模型/提示词版本、执行阶段与 query_id | 日志不包含密钥；敏感问题原文和结果按策略脱敏或不落盘 |
| 交付与恢复 | 新环境启动、版本回退、会话恢复、审计/反馈备份恢复各有成功记录 | 记录实际命令、前置条件与输出；由 Claude 在可用环境执行，本规划不预报测试成功 |

保留集不足时，先报告样本规模与局限；不要用大量同义改写冒充独立业务覆盖。若当前正确率低于目标，优先限制并修好已承诺范围，再扩展能力。

## 7. 本阶段明确不做

- 不建设完整 BI 报表平台或可视化语义建模器。
- 不同时宣称所有 SQL 方言均具备生产执行保障。
- 不实现跨库联邦查询和任意多 Agent 自主数据探索。
- 不用自研 SQL 成本优化器替代数据库优化器；没有实测收益不增加复杂重写规则。
- 不把反馈自动写回受信指标、权限或 Prompt 后直接上线。
- 不以更多模型适配、更多意图标签或 MCP 工具数量作为核心交付指标。
- 不绕过 DSL，不让模型自由定义指标，不把业务规则继续堆进 API 路由。

## 8. 推荐先交给 Claude 的工作包

先执行“第 1 周”，不要把六周拆成同时施工的任务：

1. 按项目导航阅读权限、API、DSL 与语义层文档，确认身份来源、所有入口和现有匹配契约，列出兼容风险。
2. 先提交可复现的安全和结果级失败测试：未知用户、伪造租户、索引统计改变匹配结果、F006 部分枚举值，以及 warning 下真实数据保留。
3. 实现统一可信主体和默认拒绝；修复非等价匹配改写，保留既有 DSL、权限、审计和域路由的架构约束。
4. 在 Claude 可用的 Python 环境执行定向测试和受影响回归，交付命令、解释器路径、实际通过/失败/跳过数量、未验证范围和中文文档变更。
5. 提交审阅后再进入第二周。提交仓库前检查敏感配置与测试数据；是否 commit/push 按用户当次授权执行，不将本文视为推送授权。

阶段评审时先看“未授权请求是否被挡住、业务答案是否正确”，再看功能数量与性能优化。
